## 1. Кратко

Код аккуратный. Правила расписания продуманы: заглушки пар, лимит по уникальным преподавателям, общие факультеты строки, снятие с единственной пары. Миграции идемпотентны, схема совпадает с Go-версией, типы генерируются из Rust, `svelte-check` проходит без ошибок и предупреждений.

Главные риски не в алгоритмах, а в двух местах:
1. **Ошибки не доходят до пользователя.** Большинство мутаций на фронте идут с `silent = true`, а экраны закрываются так, будто всё прошло.
2. **Бэкенд почти не проверяет входные данные.** Время, ставка, лимит, даты, имена и статусы архива проверяются только в UI, и то не везде.

Что исправлять первым:

1. **P1-1.** Преподаватель «без направления» и открепление от направления не работают: внешний ключ не допускает `direction_id = 0`. Подтверждено SQLite-проверкой.
2. **P1-2.** Ошибки мутаций молча проглатываются, а экраны закрываются как при успехе. Правка теряется без сообщения.
3. **P1-3.** Сбой на старте (битый конфиг, недоступная БД) приводит к `expect`, и приложение молча не открывается.
4. **P1-4.** Время пары не проверяется: можно создать «10:00–09:00» или «9.40». Сравнение времени строковое.
5. **P1-5.** Удаление временного слота одним кликом, без подтверждения, со снятием всех назначений.
6. **P1-6.** Отвязка и архивация преподавателя не снимают его назначения. Назначения становятся невидимыми и занимают лимит слота.
7. **P1-7.** Бэкенд не проверяет правила из `AGENTS.md`: `rate > 0`, `teacher_count >= 1`, непустые имена, формат и порядок дат, статус архива при привязке.

Остальные находки перечислены по областям в разделах 5–12. Решения, которые нужны от владельца, собраны в разделе 16.

### P1-1. «Без направления» и открепление от направления падают на внешнем ключе

- **Где:** `frontend/src/lib/components/teachers/teacher-edit.svelte:78` (пункт «Без направления» со значением `0`); `frontend/src/lib/components/directions/direction-edit.svelte:60` (открепление пишет `directionId: 0`); `src-tauri/src/storage/schema.sql:20-22` (внешний ключ `direction_id → directions(id)`); `src-tauri/src/storage/db.rs:20-22` (`PRAGMA foreign_keys = ON`).
- **Что происходит:** в таблице `directions` нет строки с `id = 0`. Поэтому вставка и `UPDATE` с `direction_id = 0` отклоняются. Фронт вызывает `addTeacher` и `updateTeacher` с `silent = true` (`stores/teachers.ts:51`, `:65`), ошибка не показывается, экран закрывается.
- **Проверено:** SQLite по схеме проекта. Вставка с `direction_id = 0` даёт `FOREIGN KEY constraint failed`. `UPDATE ... SET direction_id = 0` даёт то же. Переименование без смены направления проходит.
- **Не регрессия порта.** В Go тот же дефект: та же схема, `PRAGMA foreign_keys = ON` (`backend/storage/database.go:44`), тот же пункт «Без направления» (`teacher-edit.svelte:89` в legacy). Но в Go ошибки в основном показывались алертом, поэтому дефект был заметнее.
- **Усугубляющий фактор:** миграция `db.rs:38` добавляет колонку `direction_id ... DEFAULT 0` для старых баз. У пользователя могут уже лежать преподаватели с `direction_id = 0` (проверка в разделе 18).
- **Решение (Q-1):** вариант Б сейчас, вариант А — после полного удаления Go-версии.
- **Что сделать** (варианты, см. Q-1):
  - Если «без направления» нужно: сделать `direction_id` допускающим NULL. SQLite не умеет снять `NOT NULL` через `ALTER`, понадобится идемпотентная миграция с пересозданием таблицы `teachers` по образцу `safe_columns`. Учесть Go-версию: `backend/storage/teachers.go:65` сканирует `direction_id` без `sql.Null*`, на NULL чтение упадёт (см. раздел 14).
  - Если не нужно: сделать направление обязательным в форме, а «открепить» заменить на «перевести в другое направление». Старые строки с нулём исправить миграцией данных.
  - В любом случае убрать `silent` для этих операций (см. P1-2).

### P1-4. Время пары не проверяется, сравнение времени строковое

- **Где:**
  - `frontend/src/lib/components/schedule/schedule-screen.svelte:275-277`: поля «Начало» и «Конец» — обычные текстовые `input`, не `type="time"`, без проверки;
  - `src-tauri/src/schedule.rs:295-319`: `add_slot` не проверяет формат, `start < end`, длительность;
  - `schedule.rs:15-22`: `normalize_time` оставляет «9.40» как есть, превращает «a:b» в «0a:0b», диапазоны не проверяет;
  - `src-tauri/src/storage/repo.rs:394`: `ORDER BY day_of_week, start_time`, сортировка строковая.
- **Проверено SQLite:** `'9:00' < '10:00'` даёт 0, то есть «9:00» сортируется после «10:00». Строка «09:00» сортируется верно.
- **Последствия:** можно создать «10:00–09:00», «9.40–11.15» или «25:00–26:00». Мусор попадает в БД, в ключи слотов и в экспорт. Порядок строк сетки ломается, если в данных есть ненормализованное время (см. B-21).
- **Что сделать:** на бэкенде проверять формат `HH:MM`, диапазоны часов и минут, `start < end`, пересечения с другими парами того же дня и точный дубль (Q-4: пересечения обязательны). По умолчанию выбор из стандартных пар ТулГУ, 95 минут каждая (Q-4). Фронт предлагает именно их, бэкенд без признака «нестандартное время» принимает только их. Кнопка «Нестандартное время» открывает свободный ввод, где длительность не проверяется (Q-4). Границы дня (07:45–19:10) пока не проверяем. `normalize_time` должен возвращать ошибку вместо «угадывания». Для существующих данных проверить (раздел 18) и при необходимости нормализовать.
- **Коды ошибок (новые):** `invalid_time` (формат), `start_not_before_end`, `slot_overlaps` (пересечение), `not_standard_pair` (стандартный режим, время не из списка). Тексты переводит фронтенд (`ru.json`).
- **Где менять:** `schedule.rs` (`add_slot`, `build_view`, список стандартных пар), `commands.rs` (`AddSlotRequest`: признак нестандартного времени), `frontend/src/lib/components/schedule/schedule-screen.svelte` (поповер «Добавить пару»), `frontend/src/lib/locales/ru.json`. После изменения структур Rust — `pnpm gen:types`.

### P1-6. Отвязка и архивация не снимают назначения: назначения становятся невидимыми

- **Где:**
  - `src-tauri/src/storage/repo.rs:375-384` (`unbind_teacher` удаляет только строку `semester_teachers`);
  - `repo.rs:196-205` (`archive_teacher` ставит только флаг);
  - `schedule.rs:117` (в сетку попадают только привязанные);
  - `schedule.rs:119` и `:170` (`assigned` и `teacher_current` считают всех назначенных, в том числе непривязанных);
  - `commands.rs:402-405` (экспорт использует только привязанных).
- **Что происходит:** непривязанный преподаватель продолжает занимать лимит слота (`teacher_current/teacher_max`), но колонки в сетке для него нет, и снять назначение в UI нельзя. Единственный способ — заново привязать его к семестру.
- **Совпадает с Go-версией** (сверка, пункт 1): дефект унаследован. Для UI он тупиковый, поэтому P1.
- **Решение (Q-2, третий раунд):** при снятии привязки назначения преподавателя в этом семестре удаляются автоматически, теми же правилами, что и ручное снятие галочки (пары, заглушки). Архивный преподаватель остаётся в расписании вместе со своими назначениями. Сохранять галочки для возврата не нужно: после повторной привязки их ставят заново.
- **Что сделать:** в одной транзакции снимать назначения при отвязке. Логика та же, что у ручного снятия (`schedule.rs:200-215`). Показывать, сколько снято. Подтверждение перед снятием: диалог с числом назначений и пар; после снятия — уведомление с итогом (решено, Q-2).

### P1-7. Бэкенд не проверяет правила из `AGENTS.md`

- **Ставка.** `commands.rs:173-184` (`TeacherRequest.rate: f64` без проверки), `repo.rs:161-174` и `:186-194`. `AGENTS.md` требует `rate > 0`. Отрицательная ставка проходит: фронт (`teacher-edit.svelte:20`) проверяет только `Number.isFinite`. Ноль отсекает `!data.rate` в `save()` (`:45`), и тогда экран молча ничего не делает.
- **Лимит.** `schedule.rs:295-319` и `commands.rs:357-363` (`teacher_count: i64` без проверки `>= 1`). Лимит 0 или отрицательный делает слот неназначаемым.

- **Даты семестра.** `commands.rs:263-266`, `repo.rs:230-248`, `repo.rs:271-280`: нет проверки формата `YYYY-MM-DD` и `start <= end`. Сортировка `ORDER BY start_date DESC` (`repo.rs:263`) верна только для ISO. Проверка `end >= start` есть только на фронте (`semester-edit.svelte:25`).
- **Статус архива при привязке: преподавателя снято (Q-3).** Привязка архивного преподавателя разрешена и нужна: человек может вернуться на один семестр. - **Статус привязки при назначении.** `schedule.rs:195` (`toggle_teacher`) не проверяет, что преподаватель привязан к семестру. Сетка показывает только привязанных, но API это позволяет.
- **Что сделать:** слой валидации в командах и репозитории с кодами ошибок (`AGENTS.md`: коды, тексты переводит фронтенд). На фронте добавить подсказки до отправки. Правила уточнить по Q-3, Q-4, Q-5.

## 16. Вопросы владельцу

Статус: все вопросы решены, включая уточнения четвёртого раунда и выбор времени пары в интерфейсе (Q-4). Границы дня отложены. Идея снимка базы и диагностического пакета записана в разделе 19 как предложение, решения нет.

Решения ниже определяют правки. Где текст разделов 4–14 расходится с решением, действует раздел 16.

- **Q-1. Преподаватель без направления.** Нужен ли такой случай? Если нет, направление обязательно, а «открепить» превращается в «перевести». Если да, нужна миграция `direction_id` в NULL, и тогда Go-версия, скорее всего, перестанет читать базу (см. Q-9).
  - **Ответ:** да, преподаватель может быть без направления.
  - **Что это значит:** код уже считает `0` признаком «без направления» (`schedule.rs:183`), и фронт тоже (пункт «Без направления» в `teacher-edit.svelte`). Мешает только внешний ключ `teachers.direction_id → directions(id)`. Варианты:
    - **А.** NULL в `direction_id`. Нужна пересборка таблицы `teachers`. Go-версия не сможет прочитать строки с NULL: она читает `direction_id` в поле без `sql.Null*` (`backend/storage/teachers.go:65`).
    - **Б.** `0` как «без направления», внешний ключ у `teachers.direction_id` убрать. Тоже пересборка таблицы. Go-версия продолжит работать: `0` она читает нормально, а `LEFT JOIN` с `sql.NullString` уже обрабатывает пустое название.
    - **Решение: Б** сейчас, пока Go-версия остаётся запасным вариантом (Q-9). Переход на **А** — после полного удаления Go-версии. Внешний ключ почти ничего не защищает: направления в приложении не удаляются, только архивируются. Вариант Б также узаконивает старые строки с `direction_id = 0` из миграции `db.rs:38`.
- **Q-2. Отвязка и архивация преподавателя с назначениями.** Снимать назначения автоматически (с предупреждением) или запрещать операцию, пока назначения есть? Что делать с непривязанным преподавателем в лимите слота?
  - **Ответ (второй раунд):** не А и не Б. Назначения при снятии привязки сохранялись, чтобы их было легко вернуть; архивный преподаватель остаётся в расписании. Заменено решением третьего раунда ниже.
  - **Решение (третий раунд):** при снятии привязки назначения удаляются автоматически, как при ручном снятии галочки. Архивный преподаватель остаётся в расписании с назначениями. Последствие: после повторной привязки галочки ставятся заново. Подтверждение перед снятием: да, диалог с числом назначений и пар. После снятия — уведомление с итогом (решено по вашему «решай сам»).
  - **Пояснение:**
    - Есть два действия, которые убирают преподавателя из семестра. «Снять привязку» в окне «Привязка преподавателей» на экране расписания: преподаватель пропадает из списка семестра, и его колонка исчезает из сетки. И «Удалить» в списке преподавателей: по сути это архивация, преподаватель уходит из общего справочника.
    - Проблема в назначениях, то есть в крестах «+» в ячейках сетки. При снятии привязки они остаются в базе. Колонки уже нет, поэтому назначение не видно и снять его нельзя. Но оно продолжает занимать место в лимите слота. Например, слот показывает «1/2», хотя этого преподавателя в сетке не видно. Это тупик.
    - **Вариант А.** Автоматически: при снятии привязки или архивации система снимает все его назначения в этом семестре. Перед этим показывается подтверждение с числом пар, которые освободятся.
    - **Вариант Б.** Запрет: операция не выполняется, пока есть назначения, и система показывает, где они. Назначения сначала снимаются вручную.
    - Вторая часть вопроса («что делать с непривязанным в лимите слота») касается старых невидимых назначений, которые уже лежат в базе: учитывать их в лимите или нет. При варианте А или Б новые такие назначения не появятся. Старые надо один раз разобрать (проверочный запрос — в разделе 18).
    - Варианты А и Б из пояснения отклонены (см. ответ выше). Пояснение оставлено для контекста.
- **Q-3. Архивные в привязке.** Можно ли привязывать архивного преподавателя или архивный семестр? Должны ли уже назначенные архивные преподаватели оставаться в сетке?
  - **Ответ (уточнение):** да, привязка архивного преподавателя разрешена и нужна: человек может вернуться на один семестр (например, преподаватель подрабатывает и вернулся на один семестр). При создании нового семестра архивные не привязываются автоматически (в коде `create_semester` берёт только `isArchived = FALSE`). Их добавляют вручную из архива в окне «Привязка преподавателей».
  - **Пояснение:**
    - В окне «Привязка преподавателей» видны все преподаватели, включая архивных. У архивных стоит пометка «Архив», но кнопка «Добавить преподавателя» доступна. То есть архивного преподавателя можно привязать к семестру. Исходная оценка «не нужно» снята ответом выше.
    - Второй вопрос про случай, когда преподаватель уже привязан и назначен в сетку, а потом его отправили в архив. Сейчас его колонка остаётся в сетке и в экспорте. Пометки «архив» в самой сетке нет, она есть только в окне привязки. Оставлять так или скрывать архивных в действующем семестре? Если скрывать, назначения снова станут невидимыми, как в Q-2.
    - Архивный семестр из интерфейса не открыть: в архиве доступна только кнопка «Восстановить». Поэтому вопрос касается только преподавателей.
    - Подвопросы решены: (а) запрещать привязку архивных не нужно; (б) архивный преподаватель, уже привязанный к семестру, остаётся в расписании. По экспорту явно не подтверждено: логика та же, привязанные попадают в экспорт.
- **Q-4. Слоты.** Допускаются ли пересекающиеся интервалы в одном дне? Минимальная и максимальная длительность пары? Ограничения на начало и конец (например, рабочие часы)?
  - **Ответ:** «нет». Уточнено: нужна валидация, чтобы строки расписания одного дня не пересекались по времени. В интерфейсе «пара» — это строка расписания (кнопка «Добавить пару» создаёт слот), поэтому речь о слотах. Пары внутри одного слота и так имеют одинаковое время.
  - **Ответ (четвёртый раунд):** пара 95 минут. Стандартные пары в ТулГУ: 7:45–9:20, 9:40–11:15, 11:35–13:10, 13:40–15:15, 15:35–17:10. Физруки используют далеко не все. Границы дня (07:45–19:10) пока не важны, не проверяем.
  - **Решение по интерфейсу:** стандартные пары по умолчанию, свободный ввод по кнопке.
    - В «Добавить пару» по умолчанию выбор из стандартных пар, которых ещё нет в этом дне. Если пара не выбрана, при создании показываем подсказку «Выберите время пары».
    - Кнопка «Нестандартное время» открывает текущий ввод «Начало» и «Конец». Длительность там не проверяется. Кнопка «Стандартное время» возвращает выбор из списка.
    - В обоих режимах всегда проверяются формат `ЧЧ:ММ`, «начало раньше конца», пересечение с другими парами этого дня и точный дубль.
    - Список стандартных пар хранится на бэкенде как константа, фронт получает его вместе с сеткой. Бэкенд без признака «нестандартное время» принимает только стандартные пары, иначе отказ. Решение по реализации принято по вашему «решай как хочешь».
    - Схему БД не меняем: время хранится как `ЧЧ:ММ`, совместимость с Go сохраняется. В журнале (Q-8) добавление пары пишем с признаком «нестандартное время» и результатом.
  - **Следствие:** пересечения проверяем всегда, в том числе для нестандартного времени, где они возможны. Сейчас `add_slot` отвергает только точный дубль (`schedule.rs:299`): формат, порядок и пересечения не проверяются. Существующие базы проверяем на пары вне стандартного набора и на пересечения (запросы в разделе 18). Такие пары не удаляем автоматически, решаем вручную.
- **Q-5. Ставки.** Только шаг 0,25 или любое положительное значение? Округление цели `rate × 12` (сейчас `round`, `schedule.rs:129`)?
  - **Ответ:** да, только шаг 0,25.
  - **Следствие:** ставка должна быть положительной и кратной 0,25. Тогда `rate × 12` всегда целое (кратно 3), и вопрос об округлении отпадает. Значения, введённые вручную (поле ввода этого не запрещает), надо проверить: `rate × 4` должно быть целым числом.
- **Q-6. Лимит `teacher_count`.** Должна ли быть команда изменить лимит существующего слота (сейчас только пересоздание)? Лимит — свойство слота или максимум по парам (сейчас максимум, и удаление пары может его уменьшить)?
  - **Ответ:** давай сделаем.
  - **Подтверждено:** нужна команда «изменить лимит слота», лимит — свойство слота, а не максимум по парам. Это закрывает B-11. Возможный способ: держать одинаковый `teacher_count` во всех парах слота и менять его разом в одной транзакции. Миграция схемы для этого не нужна.
- **Q-7. Очистка строки.** Нужна ли операция «очистить назначения строки» отдельно от «удалить строку»?
  - **Ответ:** давай сделаем.
  - **Следствие:** в интерфейсе две операции. «Очистить назначения»: пары слота остаются заглушками с тем же лимитом и факультетами. «Удалить строку»: только с подтверждением (P1-5).
- **Q-8. Журнал.** Что логировать: запросы и ответы как в Go, архивацию при выходе? Можно ли писать ФИО в журнал?
  - **Ответ (уточнение):** в журнале можно писать всё, включая ФИО. Журнал нужен, чтобы по нему было понятно, что делал пользователь в программе, и чтобы это можно было повторить. Значит, это журнал действий, а не поток технических строк. Без шума («срача»).
  - **Следствие (предложение):**
    - пишем операции, которые меняют данные или показывают результат (создание, изменение, назначение и снятие преподавателя, привязка, архивация, факультеты и слоты, экспорт): одна строка на операцию, с параметрами (id и названия) и результатом (успех или код ошибки);
    - клики и навигацию не пишем: это правило `AGENTS.md`, и для повторения операций оно не мешает;
    - ошибки пишем с именем операции, кодом и технической причиной;
    - без дампов запросов и ответов;
    - ротация по дням и по размеру (не решено, предложение);
    - ФИО в журнале допустимы, замена на id не нужна.
  - **Открыто:** для точного повторения одного журнала может не хватить копии базы. Идея записана в разделе 19 как предложение, решения нет.
- **Q-9. Go-запасной путь на Win7.** Остаётся ли Go-версия рабочим запасным вариантом (путь B из `docs/windows7.md`)? От этого зависит, можно ли менять схему.
  - **Ответ:** пока остаётся «на всякий случай», планируется скоро убрать.
  - **Следствие:** совместимость с Go нужна до её удаления. Это важно для варианта Б в Q-1. После удаления Go-версии ограничения схемы можно ужесточить (например, NULL в направлении).
- **Q-10. Архивация семестра из UI.** Нужна ли кнопка? В Rust она есть, в Go по сверке нет.
  - **Ответ:** да, кнопка нужна. Совпадение с Go-версией не важно.
  - **Следствие:** ничего не меняем. Паритет с Go в этом пункте не цель.
- **Q-11. Архивные направления и факультеты.** Как показывать их в сетке и экспорте: с пометкой «архив» или скрывать?
  - **Ответ:** с пометкой.
  - **Следствие:** название архивного направления или факультета остаётся видимым, с пометкой «архив», и в сетке, и в экспорте. Пустых чипов не будет (B-24, F-14).
- **Q-12. Debug-меню.** Оставить в продакшене за F11 или убрать?
  - **Ответ:** оставить, оно нужно.
  - **Следствие:** рекомендация F-26 (убрать из релиза) снимается. F11 остаётся как есть.
- **Q-13. Тексты.** Согласовать «архив» или «удаление» в подтверждениях (`AGENTS.md`: удаление — это архивация).
  - **Ответ:** «В архив».
  - **Следствие:** кнопка подтверждения архивации называется «В архив» вместо «Удалить». Текст вопроса привести к той же лексике. Точную формулировку согласуем при правке (F-07).
- **Q-14. Экспорт.** Архивные преподаватели в конце колонок (сейчас) или вперемешку, как в Go?
  - **Ответ:** вперемешку, в том порядке, в котором они были до архивации.
  - **Следствие:** архивный преподаватель не уходит в конец колонок. Сортировка по ФИО без учёта статуса архива. Сейчас в `repo.rs:314` стоит `ORDER BY t.isArchived, ...`, это надо убрать (E-02).
- **Q-15. Конфликты расписания.** Нужна ли проверка, что преподаватель не назначен на два пересекающихся по времени слота? Сейчас такого правила нет.
  - **Ответ:** не нужна. По Q-4 пересекающихся слотов в одном дне не будет.
  - **Следствие:** ответ держится на правиле из Q-4 (без пересечений в одном дне). Значит, это правило обязательно проверять на бэкенде.

## 17. Ручной чек-лист после исправлений

Проверять на копии базы, не на рабочей. Для Windows 7 отдельно.

1. Создать преподавателя без направления: успешно, направление `0` (вариант Б, Q-1).
2. Открепить преподавателя от направления: работает, направление становится `0`.
3. Переименовать направление при недоступной БД (например, файл только для чтения): ошибка видна, экран не закрывается.
4. Удалить `theme` из `config.json`: диалог с объяснением, не тихий выход.
5. Пустой `dbPath` в `config.json`: приложение отказывается открывать базу с сообщением.
6. Добавить пару (Q-4). В стандартном режиме предлагаются только стандартные пары, которых ещё нет в этом дне. В режиме «Нестандартное время» принимается любой интервал без проверки длительности, например «10:00–11:00». В обоих режимах отказ с подсказкой при пересечении с другой парой дня и при точном дубле. Введённые вручную «10:00–09:00», «9.40», «25:00» тоже отклоняются. Кнопка «Стандартное время» возвращает список.
7. Удаление строки слота: подтверждение с числами пар и назначений.
8. Отвязка преподавателя с назначениями: диалог с числом назначений; после подтверждения назначения удаляются, счёт слота верный. После повторной привязки галочки ставятся заново (Q-2).
9. Архивация преподавателя с назначениями: преподаватель остаётся в расписании с галочками.
10. Ставка 0 и −1, лимит 0: отказ с подсказкой. Ставка 0,3 (не кратна 0,25): отказ (Q-5).
11. Направления, факультеты, преподаватели с кириллицей (`Ёлка`, `абв`): порядок по алфавиту.
12. Архивный факультет в слоте: подпись видна (с пометкой), экспорт совпадает с сеткой.
13. Экспорт: диалог, сохранение, открытие в Excel и LibreOffice. Шапка, ставки, «+», объединения ячеек, архивный преподаватель (если привязан).
14. Смена темы на всех экранах.
15. Escape в модалках и поповерах; фокус остаётся в диалоге.
16. Windows 7: установка, запуск, смена темы, очистка данных (W-05), экспорт, сетка с кириллицей.

## 18. Проверочные запросы к БД (только чтение, на копии)

База пользователя лежит в `~/.tulsu-pe-timetable/timetable.db`, режим WAL. Перед проверкой закрыть приложение и скопировать вместе с файлами `-wal` и `-shm`, если они есть. Запросы только читают данные.

```sql
-- Нарушения внешних ключей (P1-1)
PRAGMA foreign_key_check;

-- Преподаватели с нулевым или несуществующим направлением (P1-1)
SELECT id, first_name, last_name, direction_id
FROM teachers
WHERE direction_id = 0 OR direction_id NOT IN (SELECT id FROM directions);

-- Пары с ненормализованным временем (P1-4, B-21)
SELECT id, start_time, end_time
FROM lessons
WHERE start_time NOT GLOB '[0-9][0-9]:[0-9][0-9]'
   OR end_time NOT GLOB '[0-9][0-9]:[0-9][0-9]';

-- Назначения непривязанных к семестру преподавателей (P1-6)
SELECT lt.lesson_id, lt.teacher_id, l.semester_id
FROM lesson_teachers lt
JOIN lessons l ON l.id = lt.lesson_id
LEFT JOIN semester_teachers st
  ON st.semester_id = l.semester_id AND st.teacher_id = lt.teacher_id
WHERE st.teacher_id IS NULL;

-- Пары с архивным или отсутствующим направлением (B-20)
SELECT l.id, l.direction_id
FROM lessons l
LEFT JOIN directions d ON d.id = l.direction_id
WHERE d.id IS NULL OR d.isArchived = 1;

-- Пары без лимита преподавателей (B-11)
SELECT COUNT(*) AS lessons_without_limit
FROM lessons
WHERE teacher_count IS NULL;

-- Семестры с некорректными датами (P1-7)
SELECT id, start_date, end_date
FROM semesters
WHERE start_date NOT GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
   OR end_date NOT GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
   OR end_date < start_date;

-- Пары вне стандартного набора (Q-4)
SELECT id, start_time, end_time
FROM lessons
WHERE (start_time || '-' || end_time) NOT IN (
  '07:45-09:20', '09:40-11:15', '11:35-13:10', '13:40-15:15', '15:35-17:10'
);

-- Пересекающиеся пары одного дня и семестра (Q-4; запускать после проверки формата времени)
SELECT a.id AS lesson_a, b.id AS lesson_b, a.semester_id, a.day_of_week,
       a.start_time, a.end_time, b.start_time, b.end_time
FROM lessons a
JOIN lessons b
  ON b.semester_id = a.semester_id
  AND b.day_of_week = a.day_of_week
  AND b.id > a.id
  AND a.start_time < b.end_time
  AND b.start_time < a.end_time
  AND NOT (a.start_time = b.start_time AND a.end_time = b.end_time);

-- Целостность файла
PRAGMA integrity_check;
```

### 19.1. Снимок базы и диагностический пакет

**Зачем.** Журнал действий нужен, чтобы понять, что делал пользователь, и повторить это. Повтор работает только на том же состоянии базы, поэтому одного журнала может не хватить.

**Что предлагается:**
- **Снимок базы.** Копия `timetable.db` в папке `logs/snapshots/` рядом с журналом. Момент снимка: при каждом старте (храним последние N) или только при ошибке (открыто). Делать копию через `VACUUM INTO` или backup API SQLite, а не копированием файла: в режиме WAL копия одного файла `timetable.db` может не включать данные из `-wal`.
- **Диагностический пакет.** Кнопка «Сохранить диагностику»: собирает ZIP из журнала действий, снимка базы и `config.json`. Пакет создаётся только по нажатию пользователя и никуда не отправляется сам. Кнопка подходит для дебаг-меню (F11), которое оставляем (Q-12).
- **Повтор.** На копии снимка по порядку проигрываются операции из журнала. Журнал записывает каждую операцию, которая меняет данные, с параметрами (id и названия) и результатом (решено в Q-8). Тогда ошибку можно воспроизвести, не работая с машиной пользователя.

**Риски и ограничения:**
- В снимке и журнале персональные данные (ФИО, названия). Пакет только по инициативе пользователя. Снимки ограничить по числу или сроку хранения.
- Размер базы не проверен: файл не открывали. Для небольшой базы снимок при каждом старте дёшев, но это нужно подтвердить.
- Повтор работает, если операции воспроизводимы: одинаковые id и порядок. Операции с текущим временем (например, имя файла экспорта) при повторе дадут другой результат. Журнал пишет результат, поэтому расхождение будет видно.

**Порядок, если решим делать:** сначала журнал операций (Q-8), затем снимки, затем пакет. Инструмент повтора последним.

**Открыто:**
- снимок при каждом старте или только при ошибке;
- сколько снимков хранить;
- кнопка только в дебаг-меню или и в основном интерфейсе;
- нужен ли отдельный инструмент повтора или хватит ручного разбора журнала.
